# A checkpoint marker for audit.py

## Context

A full-transcript comparison against the compiled original, turn for turn, is real and found real bugs - but it cannot see past the first place the original and the port roll independent dice. Once the troll or the thief takes a different number of rounds to fall on one side than the other, every line after that point compares two different histories rather than two answers to the same question, and the whole rest of a five-hundred-command transcript reads as noise.

Both interpreters already save and restore mid-session - `dfrotz`'s own `save`/`-L`, and `stage play`'s own `save <name>`/`load <name>` - confirmed directly before any of this was built, rather than assumed.

## Decision

A script line of the form `@checkpoint name` is not sent to either game. `tools/audit.py` reads it as an instruction to itself: split the script into segments at each one, and for each segment boundary, save both interpreters' state under that name the first time it is reached. A later run that finds both files already on disk skips straight to loading them and does not replay - or re-diff - anything before that point at all.

Placement matters: a marker belongs right after a fight resolves, not mid-fight. What a checkpoint buys is a clean floor to stand on afterward, not synchronised dice - the segment containing the fight itself is still exactly as noisy as before, and is meant to be; only the segments after it stop inheriting that noise.

Two offsets, found by testing rather than assumed and got wrong once before being fixed: resuming costs `dfrotz` exactly one extra leading reply (the restore's own "Ok.", since `-L` preloads before the interactive loop starts at all), and costs the port two (the ordinary opening banner, then `load`'s own reply, since the port treats loading as a command like any other rather than something the process starts already inside). Getting this wrong does not crash anything - it silently shifts every comparison in a resumed segment by one, which reads exactly like a real difference until traced.

## Consequences

Checkpoints are not tracked - `tools/checkpoints/*.qzl` and the port's own `<game>.saves/*.save.json` are regenerated by running the script once, the same way a built `.stg` is. Iterating on a puzzle deep in the game no longer means refighting the troll and the thief first, on both sides, every time. Confirmed directly: deleting one checkpoint and re-running recaptures only the segment that produces it, leaving every other checkpoint's file untouched (checked by hash, not by eye).

What this does not do is make combat comparable. A segment that contains a fight is exactly as noisy after this as before it - the value is entirely in what happens *after* a fight, which no longer inherits that noise. Running the full walkthrough with two markers (`post-troll`, `post-thief`) found the same turn-budget fragility on both interpreters independently: the lamp's own battery, tuned to ZIL's real 185-turn life, is close enough to the padding a fight's own unpredictability demands that an unlucky run can still end in the dark before reaching a second light source. Real, and the same on both sides, so not a difference this tool exists to catch - a walkthrough-tuning problem, not a port bug or a tool bug.

## Alternatives

**Synchronising the two interpreters' randomness** was never on the table: `dfrotz` and Stage carry entirely different RNGs, built independently, and nothing about matching their outputs bit for bit was a design goal worth chasing - a checkpoint sidesteps the question rather than answering it, which is the right amount of ambition for what this needed to do.
